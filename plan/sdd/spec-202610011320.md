# SPEC — GeekHunter como segunda fonte, mesmo front

Timestamp: `202610011320`

## Objetivo

Adicionar o **GeekHunter** como segunda fonte de vagas do `linkedin-laya`,
reutilizando o mesmo dashboard estático e o mesmo classifier Laya, seguindo o
padrão de pluggability do `zackangelo/gkhr-interview-assistant` (provider
isolado atrás de uma interface, config por env, degradação explícita quando o
provider não está disponível).

## Contexto

- Hoje o pipeline é 100% LinkedIn: `LinkedInBrowserClient` (Patchright) →
  `extract_job_items` → `upsert_job` → classifier → SQLite → `GET /jobs` →
  dashboard estático.
- O GeekHunter é público e sem login: `https://www.geekhunter.com/pt/vagas`
  renderiza server-side e expõe JSON-LD (`ItemList`) com URL + título de cada
  vaga, mais cards com senioridade, modalidade e local. Busca documentada no
  `SearchAction` do site: `/pt/vagas?searchTerm={q}&experienceLevel={s}&workModality={m}&cityName={c}&page={n}`.
- O dashboard (`app/static/`) consome `JobOut` normalizado — não precisa
  mudar de forma, apenas ganhar filtro/seleção de fonte.

## Padrões de referência (gkhr-interview-assistant)

1. **Interface por provider**: `TelnyxClient` (Protocol) / `HttpTelnyxClient`
   (impl) → aqui: `JobSource` (Protocol) / `LinkedInSource` / `GeekHunterSource`.
2. **App factory com DI**: `createApp(config, dependencies)` → aqui: fontes
   construídas por `build_sources(settings)` e injetáveis nos endpoints
   FastAPI (mesmo estilo do `Depends(get_tools)` existente).
3. **Config por env com defaults**: `config.ts` (zod) → aqui: `Settings`
   (pydantic-settings) ganha chaves `geekhunter_*`.
4. **Degradação explícita**: provider sem credencial retorna erro
   `missing_config` claro → aqui: fonte indisponível não derruba o sync das
   demais; erro por fonte é reportado no response.
5. **Campos de provider separados do domínio**: `provider*` no `Call` →
   aqui: `source` + `source_id` + `raw` no `Job`; o domínio normalizado
   (score, match, decision, reasons, gaps) continua igual.
6. **Fases com checkboxes** (`PLAN.md`) → aqui: este spec + o todo
   correspondente, seguindo o fluxo SPEC → TDD → TASK → CODING do CLAUDE.md.

## Requisitos funcionais

- RF1: `POST /jobs/sync` aceita `source: "linkedin" | "geekhunter" | "all"`
  (default `"linkedin"`, mantém compat com o front atual e com clients
  existentes).
- RF2: `GET /jobs` aceita filtro `source` (opcional).
- RF3: `JobOut` expõe `source`; o card do dashboard mostra um chip com a
  fonte.
- RF4: A fonte GeekHunter coleta vagas via HTTP (httpx) + BeautifulSoup,
  sem browser e sem sessão de login.
- RF5: Vagas do GeekHunter passam pelo mesmo `upsert_job` e pelo mesmo
  classifier Laya/heurístico — nenhuma mudança de política de score.
- RF6: O dashboard ganha `<select>` de fonte no formulário "Buscar e
  classificar" e filtro de fonte ao lado dos filtros existentes — mesmos
  arquivos `index.html`/`app.js`/`style.css`, sem build step.
- RF7: Deduplicação por `(source, source_id)` — a mesma vaga re-sincronizada
  atualiza, nunca duplica.

## Requisitos não funcionais

- RNF1: Parser do GeekHunter testado com fixture HTML local (sem rede em
  testes), mesmo padrão de `tests/fixtures/`.
- RNF2: `ruff`, `bandit -ll`, `pre-commit` e suíte `pytest` verdes.
- RNF3: Sem mudança no formato de `decision`/`reasons`/`gaps` (contrato do
  Laya preservado).
- RNF4: URLs de vaga passam pelo `safeUrl` do front (já existente).
- RNF5: Nenhuma tool de escrita; GeekHunter também é somente leitura.
- RNF6: Retry/backoff simples e `timeout` no httpx; user-agent identificável.

## Restrições e decisões de design

- **Modelo**: adicionar `source: Mapped[str]` (default `"linkedin"`) e
  renomear `linkedin_id` → `source_id`, com `unique=True` em
  `(source, source_id)`. SQLite em dev: como é MVP local, a migração pode
  recriar as tabelas via `init_db` (dados de dev são descartáveis); se houver
  dados valiosos, script de migração `ALTER TABLE` antes do rename.
- **Compatibilidade**: `LinkedInJobItem` e tools `/tools/*` continuam
  inalterados (escopo LinkedIn, somente leitura).
- **Normalização**: item GeekHunter vira o mesmo dict esperado por
  `upsert_job` (`source`, `source_id`, `title`, `company`, `location`,
  `remote`, `url`, `description`, `posted_at`, `raw`).
- **`remote` do GeekHunter**: modalidade `remote`/`hybrid`/`on-site` →
  `remote = (modality == "remote")`; modalidade original fica em `raw`.
- **location**: no GeekHunter o parâmetro é `cityName`; aceitamos o campo
  `location` do request como texto livre e ignoramos quando não mapear
  (busca fica por keyword) — sem 422.

## Fora de escopo (desta iteração)

- Candidatura automática ou qualquer tool de escrita.
- Autenticação/contas no dashboard.
- Frontend com build step (continua vanilla JS).
- Multi-provider além de linkedin/geekhunter (a interface permite, mas só
  essas duas entram).
- Roadmap de produção do exemplo (auth, webhooks assinados) — não aplica.

## Critérios de aceite

- [ ] `POST /jobs/sync {"keywords":["SRE"],"source":"geekhunter"}` retorna
      `{"synced": n}` com vagas normalizadas e classificadas, sem browser.
- [ ] `source="all"` roda as duas fontes; falha de uma fonte não derruba a
      outra (response informa erro por fonte).
- [ ] `GET /jobs?source=geekhunter` filtra; `GET /jobs` sem filtro lista
      tudo; `JobOut` inclui `source`.
- [ ] Deduplicação por `(source, source_id)` verificada por teste.
- [ ] Parser GeekHunter coberto por fixture (lista + detalhe) sem rede.
- [ ] Dashboard: select de fonte no sync, filtro de fonte, chip de fonte no
      card — testes de dashboard atualizados.
- [ ] `make lint` + `make test` verdes; pre-commit passa.

## Riscos

- **HTML do GeekHunter muda** → mitigado por fixtures versionadas e parser
  defensivo (JSON-LD primeiro, cards como fallback).
- **Rate-limit/bloqueio** → mitigado por delay configurável
  (`geekhunter_delay_seconds`) e page-size conservador.
- **Conteúdo em PT-BR vs perfil em EN** → classificador já lida com
  keywords; gaps podem aumentar — aceitável, é o mesmo comportamento
  esperado para qualquer fonte externa.
