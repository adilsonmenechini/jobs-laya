## Contexto e objetivo
A auditoria de confiabilidade (04/10) apontou duas falhas em `app/sources/`:
(1) **client leak** — `GeekHunterSource`/`GupySource`/`IndeedSource` criam um `httpx.AsyncClient`
no `__init__` e nunca o fecham; cada `POST /jobs/sync` constrói um registry novo
(`build_sources()`) com 3 clientes e os abandona (3 × pool de sockets por sync em servidor longo);
(2) **`_source_id` instável no GeekHunter** — o ID é o slug (último segmento do path,
`geekhunter.py:41-42`): slugs iguais de empresas diferentes colidem no dict de
`parse_search_page` e no `upsert_job` (sobrescrita silenciosa → score distorcido), e um
rename de slug upstream gera linha nova (duplicata). Esta SPEC fecha as duas.

## Requisitos
- R1: `JobSource` (`app/sources/base.py`) ganha `async def aclose() -> None` no Protocol;
  `GeekHunterSource`/`GupySource`/`IndeedSource` fecham o próprio `httpx.AsyncClient`;
  `LinkedInSource`/`GlassdoorSource` implementam no-op documentado (recursos geridos fora: sessão
  global do browser fechada no `lifespan`; engine do Glassdoor já é fechado no `finally` de `search`).
- R2: `sync_jobs` fecha **todo** registry que ele próprio construiu (`sources is None`) num
  `finally`, cobrindo qualquer caminho de saída — sucesso, falha do `resolve_sources` (503) e
  exceções; registry injetado pelo chamador **não** é fechado (ownership de quem injeta).
  `resolve_sources` para de construir internamente (registro vira requisito): quem constrói,
  fecha — nenhum caminho "constrói e descarta" sobra.
- R3: `_source_id(url)` do GeekHunter passa a retornar o **path completo normalizado**
  (ex.: `pt/ntt-data/jobs/site-reliability-engineer--sre--3`) — inclui o company slug, então
  elimina a colisão cross-empresa.
- R4: `parse_job_detail` prefere o **`identifier.value`** do JSON-LD `JobPosting`
  (ID interno estável, hash; evidência em `tests/fixtures/geekhunter_job_detail.html`) como
  `source_id`, com fallback para `_source_id(url)`.

## Restrições e premissas
- Premissa (não verificável offline): `identifier.value` é estável sob rename de slug — é o ID
  interno da vaga no GeekHunter (formato hash SHA-256, `name: "GeekHunter"`).
- Compatibilidade: suíte de develop (259 testes) permanece verde; fakes de teste que passam pelo
  caminho de build ganham `aclose`.
- Sem mudança de schema: `Job.source_id` continua string.
- Não depender do trabalho paralelo da branch `fix/sync-deadline-and-retry` (retry/deadline são
  outra iteração; este worktree parte de `develop`).

## Fora de escopo
- Migração de dados: linhas antigas (source_id = slug) não casam com os novos IDs — a primeira
  sync pós-deploy cria as novas linhas e as antigas ficam órfãs (efeito documentado, não migrado).
- Dedup por URL no `upsert_job` (`app/services/jobs.py`).
- Retry/backoff nas fontes e deadline do sync (branch `fix/sync-deadline-and-retry`, outra sessão).
- Classifier, modelo de dados, `LinkedInSource`/`GlassdoorSource` além do `aclose` no-op.

## Critérios de aceite

- [ ] CA4: dois jobs de empresas diferentes com o mesmo slug geram `source_id` distintos

- [ ] CA5: `parse_job_detail` devolve `source_id == identifier.value` quando o JSON-LD o traz;
      sem `identifier`, cai no path completo.
- [ ] CA6: suíte completa verde (`uv run pytest -q`) e `uv run pre-commit run --all-files` verde.

## Casos de borda
- URL do detail sem `identifier` no JSON-LD → fallback `_source_id(url)`.
- URL sem path → `_source_id` não levanta exceção.
- Exceção não prevista no meio do sync → o `finally` fecha o registry antes de propagar.
- Fonte sem `aclose` no registry construído → violação do Protocol falha alto (teste cobre o caminho).

## Riscos e decisões em aberto
- **Migração**: mudança de esquema de ID duplica na 1ª sync (linhas antigas de slug ficam órfãs).
  Decisão: documentar; limpeza é operação manual do usuário.
- **identifier como ID canônico depende de `fetch_details=True`** (default do schema); sync sem
  details ou com detail falho usa path completo — se os dois esquemas se misturarem no banco,
  pode sobrar uma linha residual. Aceito: `fetch_details=True` é o caminho normal.
- Context manager (`__aenter__`/`__aexit__`) foi considerado e rejeitado: as fontes nascem dentro
  de um registry (`build_sources()`) consumido por `sync_jobs` — `aclose()` + `finally` casa com o
  modelo de ownership injetável; CM exigiria a dupla interface em toda implementação, inclusive fakes.
