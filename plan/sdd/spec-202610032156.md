## Contexto e objetivo

A inspeção do dashboard mostrou o badge do topo dizendo `fake · …` enquanto o
rodapé dos cards dizia `backend laya`. Investigação com reprodução limpa (sync
feito nesta sessão com `CLASSIFIER_BACKEND=fake`) mostrou que **ambos os lados
contribuem**:

1. `decision.laya.backend` é `hardcoded "laya"` em
   `app/classifier/laya_job_classifier.py:117` — até o `FakeEngine`, que grava
   `model="fake", latency_ms=1.0`, produz `backend="laya"`. Reproduzido: 2
   linhas recém-classificadas com `backend=laya, model=fake`.
2. `/health` lê `settings.classifier_backend` (configuração do processo), enquanto
   o card lê o `decision` persistido. São perguntas diferentes apresentadas sem
   rótulo, então dados históricos de outra backend parecem contradição.

Objetivo: o backend exibido passa a ser verdadeiro nos dois pontos, e a UI
deixa explícito qual dos dois é configuração vigente e qual é proveniência do
card.

## Requisitos

- **R1 — proveniência verdadeira:** `decision.laya.backend` reflete o engine que
  de fato classificou: `laya` para `LayaEngine`, `fake` para `FakeEngine`.
  O caminho de fallback já grava `heuristic` (`_fallback`) e não muda.
- **R2 — rodapé do card legível:** o rodapé deixa de começar com `Laya ·` quando
  a backend não é Laya, para não ler `Laya · modelo fake · backend fake`.
- **R3 — badge rotulado:** o badge identifica que reporta a backend **ativa**
  (configuração do processo), não a que produziu os cards exibidos.
- **R4 — sem mudança de contrato:** `decision.laya` mantém as chaves `backend`,
  `model`, `latency_ms`, `answers`; `/health` mantém `classifier.backend`,
  `laya_ready`, `device`. Nada de migration.
