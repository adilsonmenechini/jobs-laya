# SPEC 202610050909

- **Status:** confirmada pelo usuário

## Contexto e objetivo

O dashboard (`app/static/`) é uma página única: sync de vagas + lista filtrada.
Não há como zerar os dados coletados sem mexer no terminal, nem como editar o
`data/profile.json` sem abrir o arquivo — e o perfil é o que drive o score.
Esta SPEC adiciona (1) um **sidebar** com três páginas (Vagas, Perfil, Dados),
(2) um botão **Clean** que apaga todas as vagas do banco, e (3) um
**formulário estruturado** que lê e salva o `profile.json` pela API.

Decisões confirmadas pelo usuário em 2026-10-05:
- Clean = **somente** as vagas do DB (`data/jobs.db`); `profile.json` e sessão
  do LinkedIn ficam intactos.
- Editor de perfil = **formulário estruturado** (não textarea de JSON).
- Sidebar = 3 itens: **Vagas · Perfil · Dados**.

## Requisitos

- R1: `DELETE /jobs` apaga todos os registros da tabela `jobs` e responde
  `{"deleted": N}` com o número de linhas removidas. Nada mais é alterado
  (perfil, sessão LinkedIn, schema do banco).
- R2: `PUT /profile` valida o payload contra o schema do perfil (reuso de
  `ProfileOut` como entrada), grava `data/profile.json` de forma atômica
  (write-temp + replace) e devolve o perfil salvo. Payload inválido → 422 com
  o detalhe do Pydantic.
- R3: GET `/profile` continua funcionando sem mudança (perfil é relido a cada
  sync em `load_profile()`; sem cache a invalidar).
- R4: Frontend ganha **sidebar** fixa com três páginas navegáveis via hash
  (`#/vagas`, `#/perfil`, `#/dados`), sem build step (vanilla JS, padrão
  atual). A home continua sendo **Vagas** com o comportamento atual intacto.
- R5: Página **Perfil**: formulário com as seções do profile (`name`,
  `titles`, `seniority`, `locations`, `remote_required`, `skills`, `focus`,
  `exclusions`). Listas editadas como campos um-item-por-linha (add/remove),
  `remote_required` como checkbox. Carrega via GET, salva via PUT, mostra
  sucesso/erro no próprio formulário.
- R6: Página **Dados**: mostra contagem total de vagas (e por fonte) e um
  botão **Clean** com confirmação explícita (dialog de confirmação — operação
  destrutiva nunca dispara em um clique só). Após o Clean, recarrega as
  contagens e a lista de vagas.
- R7: Todos os endpoints novos cobertos por testes que falham antes e passam
  depois (TDD); markup da sidebar e das páginas novas coberto nos testes de
  dashboard.

## Restrições e premissas

- API local sem autenticação (padrão atual): `DELETE /jobs` e `PUT /profile`
  não ganham auth nesta SPEC — a única salvaguarda é o confirm do front.
  Registrado em SAFETY.
- Não mudar schema do banco, nem o formato do `profile.json`, nem o contrato
  dos endpoints existentes.
- Sem framework JS nem passo de build; sem novas dependências.
- `git status` já tem `data/profile.json` modificado (unstaged) — a edição
  via formulário vai gravações futuras sobre o arquivo de trabalho; não
  commitar segredo nem sobrescrever mudança não relacionada sem avisar.

## Critérios de aceite

- [ ] CA1: `DELETE /jobs` com N vagas no banco → 200 `{"deleted": N}`; GET
  `/jobs`logo depois → `total == 0`; banco e schema continuam existentes.
- [ ] CA2: `PUT /profile` com payload válido → 200 e o arquivo `profile.json`
  no disco reflete o payload; GET `/profile` devolve o mesmo.
- [ ] CA3: `PUT /profile` com payload inválido (ex. `skills: "x"` string) →
  422 e o arquivo no disco **não** é alterado.
- [ ] CA4: dashboard serve as três páginas pelo sidebar; Vagas mantém sync +
  filtros como hoje (teste de regressão do `test_dashboard.py` continua verde).
- [ ] CA5: formulário de Perfil: preencher um campo, salvar, recarregar a
  página → valor persistido; erro de validação aparece na UI sem corromper o
  arquivo.
- [ ] CA6: Clean exige confirmação; após confirmar, vagas somem da lista e as
  contagens da página Dados zeram.
- [ ] CA7: `uv run pre-commit run --all-files` verde (ruff, bandit, gitleaks,
  pytest).

## Casos de borda

- Clean com banco vazio → `{"deleted": 0}`, UI não quebra.
- PUT /profile com lista vazia (ex. `skills: []`) → aceito (válido) ou
  rejeitado? **Decisão: aceito** — perfil sem skills é estado legítimo; o
  classificador já trata lista vazia.
- JSON malformado em `data/profile.json` pré-existente → GET /profile hoje
  estoura 500; manter comportamento (fora de escopo corrigir), mas a UI de
  Perfil deve mostrar a mensagem de erro em vez de travar em branco.
- Sync em andamento durante Clean → fora de escopo (app local, um usuário);
  não introduzir lock.
- Edição concorrente de perfil (duas abas) → last-write-wins, aceito.

## Riscos e decisões em aberto

- **Nome do método:** `DELETE /jobs` (coleção) — RESTful e não colide com
  `DELETE /jobs/{id}` (não existe hoje). Alternativa `POST /jobs/clean`
  rejeitada por não ser idempotente-semântica.
- **Delegação Maestri:** `OpenCode` (Implementador) → backend
  (`app/main.py`, `app/schemas.py`, `tests/`); recruta novo de frontend →
  `app/static/` (divisão por arquivo, nunca por feature — lição registrada);
  `OpenCode #2` (Revisor) → REVIEW ao final. Nenhum overlap de arquivos.
- Sidebar em hash-routing pode dividir `app.js`; se crescer, separar em
  `app.js` + `pages.js` fica para o agent de frontend julgar (sem build step
  mantido).
