# SPEC — Estrutura de eval (ablação de 3 screeners)

Timestamp: 202610011438

## Objetivo

Avaliação do classificador: um dataset pequeno rotulado à mão + um
script `evaluate.py` que roda a **ablacao de 3 screeners** no mesmo dataset e gera um
relatório. Serve para mostrar a contribuição de cada parte (heurística, Laya, política
combinada) e para calibrar os thresholds (80/60) com evidência em vez de achismo.

## Escopo

### 1. Dataset — `eval/samples/`

- ~18 vagas fictícias, escritas à mão, em JSON (`*.json`), campos no formato
  que o classifier já espera: `title`, `company`, `location`, `remote`,
  `description`.
- Mix: 12 EN / 6 PT-BR; senioridades junior→staff; remoto e híbrido;
  domínios SRE/DevOps/Platform/AI (dentro do perfil) e fora
  (sales, frontend, QA, design...).
- Casos difíceis de propósito, para a ablação mostrar diferença:
  - vaga com cargo certo mas keywords de cloud espalhadas (title match vs skill spam);
  - vaga junior só com keywords (heurística fácil de enganar);
  - vaga PT-BR sem a palavra "remote" em inglês;
  - vaga híbrida para um perfil `remote_required: true`;
  - vaga de DevOps cuja descrição é sobre outra coisa.
- **Nada de dados reais do LinkedIn/GeekHunter no repo.**

### 2. Rótulos — `eval/samples/labels.json`

Formato espelhando o original:

```json
[
  {
    "file": "senior-sre-remote-en.json",
    "lang": "en",
    "expected": "high",
    "profile": "default",
    "note": "caso limpo: cargo + skills + remoto"
  }
]
```

- `expected`: `high | medium | low` — o match que a política combinada
  *deveria* dar para o perfil em `data/profile.json`.
- `note`: o porquê do rótulo (como o `note` do original), obrigatório nos
  casos não óbvios.

### 3. Script — `eval/evaluate.py`

Espelha o `evaluate.py` original:

- Carrega `labels.json`, itera as vagas, roda os **três screeners** na mesma
  vaga:
  1. **Heurística only** — `LayaInspiredClassifier.classify(job)` puro;
  2. **Laya only** — score calculado só com as respostas do modelo:
     `title` = 100/0 pelo `role_family`, `skills` = `skill_fit × 100`,
     `seniority` = `SENIORITY_VALUE[...]`, `remote` = 100/0; pesos
     renormalizados sobre os componentes disponíveis (soma 0.75 → divide
     por 0.75) para o teto não ficar artificialmente em 75;
  3. **Combinado** — `LayaJobClassifier.classify(job)` (a política atual).
- Métricas por screener: acertos exatos de `expected`, acertos por classe,
  e — como o original — `match` esperado vs obtido com marcação de erro.
- Latência do Laya mediana (mesmo campo do original) quando backend real.
- Backends: `--backend laya` (default, modelo real), `--backend fake`
  (FakeEngine, smoke test sem download), `--backend heuristic`.
- Saída: escreve `eval/evaluation.md` (relatório legível) e
  `eval/results/{backend}.json` (dados brutos por vaga, para diff entre runs).

> Decisão de local: o relatório vive em `eval/` (não `docs/`) porque o repo
> não tem `docs/` e o README já é a documentação central.

### 4. Integração

- `Makefile`: target `eval` → `uv run python eval/evaluate.py`.
- README: seção "Avaliação" documentando o comando e o que a tabela significa.
- O eval **não** entra no CI (requer checkpoint ~800MB); roda sob demanda.
- `pytest` continua sem download: nenhum teste importa `eval/`.

### 5. Fora de escopo

- Fine-tuning do Laya.
- Baselines externos (SpamAssassin etc.).
- Curva ROC / F1 / MAE de score (não solicitado nesta iteração).
- Mudanças na política (`laya_job_classifier.py`) — o eval mede como está.

## Critérios de aceite

1. `uv run python eval/evaluate.py --backend fake` roda sem download e gera
   `eval/evaluation.md` + `eval/results/fake.json`.
2. `uv run python eval/evaluate.py` (backend real) roda nos ~18 samples e
   reporta a tabela de ablação 3 screeners.
3. `make eval` existe e funciona.
4. `pytest -q` e `ruff` continuam verdes; nenhum teste novo depende de modelo.
5. README documenta o comando e a leitura da tabela.
