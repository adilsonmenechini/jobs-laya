Timestamp: `202610011320`
Spec: `plan/sdd/spec-202610011320.md`
Todo/Review: `plan/tasks/todo-202610011320.md`

## Resumo

Implementada a segunda fonte de vagas (GeekHunter) no `linkedin-laya`,
reutilizando o mesmo dashboard estático e o mesmo classifier Laya, seguindo
o padrão de pluggability do `zackangelo/gkhr-interview-assistant` (provider
atrás de Protocol, config por env, registry injetável, degradação explícita).

## O que mudou

- **`app/sources/`** (novo): `base.py` (`JobSource` Protocol +
  `SourceUnavailableError`), `linkedin.py` (adapter do browser existente),
  `geekhunter.py` (httpx + BeautifulSoup/JSON-LD, sem login),
  `__init__.py` (`source_names` para o health, `build_sources` registry).
- **`app/models.py`**: `linkedin_id` → `source` + `source_id` com
  `UniqueConstraint(source, source_id)`.
- **`app/db.py`**: `migrate_legacy_jobs` — rebuild da tabela legada
  (rename + drop de índices nomeados + copy + drop), preservando linhas.
- **`app/schemas.py`**: `source` em `JobOut`; `JobSearchRequest.source`
  (`linkedin|geekhunter|all`, default `linkedin`).
- **`app/services/jobs.py`**: `SyncOutcome(count, errors)`; `sync_jobs`
 .dispatcher por fonte com isolamento de falha; `upsert_job` filtra para
  `JOB_COLUMNS`.
- **`app/main.py`**: `source` no sync (503 se fonte fora da registry) e no
  filtro `GET /jobs` (422 se desconhecida); `/health` com `sources`.
- **`app/config.py` / `.env.example`**: `GEEKHUNTER_BASE_URL`,
  `GEEKHUNTER_DELAY_SECONDS`, `GEEKHUNTER_PAGE_SIZE`, `GEEKHUNTER_TIMEOUT_S`.
- **`app/static/`**: select de fonte no sync, filtro de fonte, chip de
  fonte no card, badge com fontes, status com erros por fonte.
- **`README.md`**: seção 5 "Fontes", exemplos com `source`, árvore
  atualizada, limitações corrigidas.

## Verificação real (não só suíte)

1. **Migração do DB real**: `data/jobs.db` (14 linhas, schema legado)
   migrado com dados preservados como `source=linkedin`.
2. **Sync GeekHunter ao vivo**: `POST /jobs/sync source=geekhunter` → 5
   vagas coletadas por HTTP público, classificadas pelo Laya
   (81.72/high, 74.34/medium, …), company descrição preenchidas pelo detalhe.
3. **`source=all`**: 15 linkedin + 5 geekhunter no mesmo dashboard,
   filtros e chips funcionando.

## Bugs reais capturados pela verificação

1. **Índices nomeados no SQLite**: `ALTER TABLE … RENAME` mantém os nomes
   `ix_jobs_*` → conflito com o `create_all` da tabela nova. Só apareceu no
   DB real (a fixture de teste não tinha índices); corrigido com drop
   explícito + teste de regressão.
2. **`UNIQUE(linkedin_id)` sobrevivendo ao rename**: quebraria a dedup
   multi-fonte — por isso a migração é rebuild, não rename simples.
3. **Modelo Laya carregando no teste de sync** (4.2s): fixture autouse com
   `classifier_backend=fake`.
4. **`/health` construindo clientes** (vazamento de socket a cada 30s):
   `source_names()` sem instanciação.
5. **Bandit `B608` na migração** (SQL por concatenação de string, Medium):
   reescrita com SQLAlchemy Core (`DropIndex` + `insert().from_select()`),
   eliminando SQL manual — identificadores compilados pelo engine.

## Decisões de design

- Falha por fonte é **reportada** (`errors` no response), não propaga —
  exceto fonte fora da registry (`503`) e request inválido (`422`).
- `details(item)` (não `details(source_id)`): GeekHunter precisa da URL.
- Extras das fontes (`skills`, `modality`, `company_slug`) vivem no dict
  normalizado/`raw`, mas só colunas do model são persistidas.
- GeekHunter: JSON-LD primeiro, DOM como fallback; `remote` só faz upgrade.

## Pendências (fora do escopo)

- Filtros avançados do GeekHunter (`experienceLevel`, `workModality`).
- `modality`/`seniority` não expostos em `JobOut` (só em `raw`).
- `make login` segue necessário só para a fonte LinkedIn.
