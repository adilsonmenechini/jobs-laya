## Decisões tomadas

- **A identidade da candidatura é `(source, source_id)`, não `jobs.id`.** O note
  propunha `job_id`; nesta base isso seria um defeito. `jobs.id` é o rowid e o
  SQLite **recicla** rowid: verifiquei que com A=1, B=2 e ambos deletados, a
  próxima linha entra como 1. Ligar o card ao `jobs.id` faria o card exibir o
  título de uma vaga e levar ao link de outra, depois de um clean + resync.
  Confirmei no browser e na API que o card mantém os dados originais enquanto a
  recoleção traz uma vaga diferente.
- **D1** — `DELETE /jobs` preserva as linhas do Kanban (não apaga tudo e deixa
  o snapshot sustaining o card). É a leitura literal do note, e preserva o
  vínculo com a origem.
- **D2** — mover por botões, não drag-and-drop: o projeto tem histórico de a11y
  (testes de `axe-core`) e DnD não é operável por teclado.
- **D3** — orquestração sequencial (backend → frontend), evitando os PRs
  CONFLICTING de #17/#18 e permitindo validar no browser com a API no ar.
- **Teste de concorrência sem threads**: SQLite serializa, então threads
  dariam um teste flaky. O stale read é simulado por monkeypatch — determinístico.
- **Fases 1 e 2 na mesma branch**: o plano previa branch separada para o
  frontend, mas isso exigiria um merge intermediário, que só o usuário pode fazer.
