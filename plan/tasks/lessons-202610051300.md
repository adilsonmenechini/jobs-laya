## L1 — Timestamp e working tree são recursos compartilhados entre sessões paralelas

**Padrão:** a iteração pedida com timestamp `202610051200` já tinha a SPEC
(`plan/sdd/spec-202610051200.md`) escrita por OUTRA sessão ativa na mesma
working tree (branch `fix/sync-deadline-and-retry`, arquivos modificados 5
minutos antes). Um `git checkout` ali teria misturado dois fixes no mesmo PR
ou corromper o trabalho em andamento.

**Regra:** antes de iniciar uma iteração, checar `git status`, `git branch
--show-current`, mtimes dos arquivos modificados e a existência de
`plan/sdd/spec-<TS>.md` com o timestamp pedido. Havendo sessão paralela
ativa ou colisão de timestamp: isolar em worktree
(`.slim/worktrees/<slug>`) com branch nova a partir da base pedida, pedir
timestamp novo ao usuário e confirmar antes de `git worktree add`. Nunca
`git checkout`/`stash` na tree ocupada.

**Aplicável:** toda iteração iniciada com timestamp ou tree já em uso;
fluxos com múltiplos agentes no mesmo repositório.

## L2 — Bug-raiz de leak também vive no caminho de erro

**Padrão:** o leak de `httpx.AsyncClient` não estava só no sucesso —
`resolve_sources` também construía o registry internamente e o descartava
no `raise` de 503 (fonte não configurada). Corrigir só o caminho feliz
deixaria o mesmo vazamento no caminho de erro.

**Regra:** ao corrigir "cria recurso e nunca libera", mapear TODOS os
caminhos de saída (sucesso, erro de configuração, exceção, timeout) e
garantir que quem constrói é quem fecha (`try/finally` + ownership
explícito: injetado ≠ construído).

**Aplicável:** qualquer recurso com ciclo de vida por request (clients,
browsers, engines, sessions).
