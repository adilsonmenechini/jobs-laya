### Desvios do plano

- **Item 2.1 mudou no caminho.** O plano previa branch separada para o frontend;
  isso exigiria um merge intermediário — que só o usuário pode fazer (§6). As
  duas fases ficaram na **mesma** branch, gerando um PR único.
- **Item 1.16 sem threads, como previsto.** O teste simula a corrida
  monkeypatchando `find_kanban` para devolver `None` numa leitura já
  commitada: o INSERT bate na constraint e o recovery devolve a linha
  existente. Verifiquei à parte que a constraint **realmente** é criada no
  SQLite (segundo INSERT igual → `IntegrityError`).
- **Os dois commits do agente frontend eu mesmo fiz.** O OpenCode travou em
  "Thinking" antes do commit; o Pixel caiu com `API Error … HTTP 200` (falha
  de provider, não de código) depois de escrever o código, com 31 testes
  verdes. Nenhum dos dois agent roteirizou o próprio commit.

### Defeitos que só o browser real pegou

A API estava correta e **todos os testes unitários passavam** nos dois casos.
Ambos apareceram ao clicar `+ Add` no portal:

1. **`dataset.source_id` vs `dataset.sourceId`** — o HTML escreve
   `data-source-id`, o DOM expõe `sourceId`, e o JS lia `source_id`
   (`undefined`). O POST saía com `source_id` ausente e a API respondia 422;
   o botão ficava em "Erro: Field required" e **nenhuma candidatura era criada**.
2. **Contador desatualizado** — o card saía do DOM mas `#total` ficava com o
   número antigo: a tela dizia "3 vaga(s)" listando 2 cards.

Cada um ganhou teste que falha antes da correção (verificado reintroduzindo o
defeito) e passa depois.
