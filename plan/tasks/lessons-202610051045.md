## 1. `jobs.id` é rowid e é reciclado — nunca use como identidade de negócio

**Kind:** gotcha · **Onde:** `app/models.py` (`Job.id`), `app/db.py`

O note `PLAN-jobs-kanban` propôs `kanban_jobs.job_id` ligando a candidatura ao
`id` da vaga. nesta base isso é um defeito: `Job.id` é o rowid do SQLite, e o
SQLite **reusa** rowid liberado depois de um `DELETE`.

Verificado nesta sessão:

```python
A.id = 1   B.id = 2
db.delete(A); db.delete(B); db.commit()   # clean
C.id = 1   # <-- reusa o rowid
```

Cenário de dano: `GET /jobs` esconde uma vaga cardada → o `clean` apaga a linha
→ o próximo sync recoleta a **mesma** vaga upstream e recebe o id de outra. O
card do Kanban passa a exibir o título/empresa de uma vaga e levar ao link de
outra, sem nenhum erro em lugar nenhum.

**Regra:** identidade de negócio nesta base é `(source, source_id)` — a chave que
`upsert_job` já trata como canônica. `jobs.id` serve só para `GET /jobs/{id}`.
Para sobreviver à remoção da origem, guardar um **snapshot** dos campos de
exibição, não uma referência.

Ao validar schema novo, confirme que a constraint realmente é criada no SQLite
(`sqlite_master` + segundo INSERT deve dar `IntegrityError`) — `create_all` pode
não produzir o que se espera.

## 2. `dataset.source_id` não existe — o DOM camelCase o atributo

**Kind:** gotcha · **Onde:** `app/static/app.js` (`addToKanban`)

`data-source-id="X"` no HTML vira `dataset.sourceId` no DOM. Ler
`button.dataset.source_id` devolve `undefined` — **sem erro, sem aviso**. O
`POST /kanban` saía com `source_id` ausente, a API respondia 422, e o botão
ficava travado em "Erro: Field required" sem criar a candidatura.

Todos os testes passavam: os testes de API (que não passam pelo DOM) e os de
dashboard (que só fazem `assert "kanban" in js`).

**Regra:** a correspondência atributo↔`dataset` só é verificável no browser.
Nenhum teste que leia o `.js` como texto pega isso — o teste que protege tem de
comparar o **nome do atributo escrito no HTML** com o **nome da propriedade
lida no JS**, e é um teste de contrato, não de comportamento.

## 3. Feature de UI passa pelo browser antes de chamar de pronta

**Kind:** rule

Os dois defeitos acima foram achados clicando `+ Add` no portal Maestri, depois
de: SPEC aprovado, suíte verde, `pre-commit` verde e todos os critérios de
aceite "atendidos" pelo teste. Nenhum deles era visível sem renderizar a página.

**Regra:** para qualquer mudança de UI, o caminho de evidência inclui abrir a
página no browser e percorrer o fluxo — clicar, ver o resultado na tela, recarregar
e conferir se persistiu. Teste unitário de JS servido como texto cobre estrutura,
não comportamento.

Complemento do mesmo achado: após mexer em arquivo estático, o browser pode estar
com a versão antiga em cache e "confirmar" o bug que já foi corrigido —
`location.reload(true)` antes de concluir que a correção não funcionou.

**Kind:** feedback

código correto e não roteirizaram o próprio commit: o primeiro ficou parado em

falhou aqui. Ao assumir, avisar o agent para ele não editar por baixo.
